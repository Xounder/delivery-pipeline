# Impact Analysis — UI/UX Modernization

Scope of this document: file-level impact, explicit file-overlap flags for the orchestrator's
parallel-dispatch planning, and the **18 material corrections (`M1`–`M18`)** discovered by
validating the approved design against the actual repository.

The four **blocking** corrections (`B1`–`B4`) are defined in
[`feasibility.md`](./feasibility.md) and must be read alongside this file. The Phase 6 lane split
and per-phase validation gates live in [`dispatch-plan.md`](./dispatch-plan.md). A compact index of
all 32 constraint IDs is in [`constraints.md`](./constraints.md).

## Material Corrections (M1–M18)

Every item below is a factual mismatch between the approved design docs and the current code.
Each is actionable without further investigation.

### M1 — Calendar stylesheet must target `.brk-calendar-google`, not `.brk-calendar`

**Constraint.** All rewritten calendar CSS must be scoped to the wrapper class the code actually
renders: `.brk-calendar-google` in `apps/web/src/components/CalendarView.tsx`. Either update the
CSS to the real class, or rename the wrapper class in `CalendarView.tsx` **and** update every
reference in the same change. Do not leave a `.brk-calendar` selector with no matching element.

**Why.** design-04 specifies `.brk-calendar`; the DOM has `.brk-calendar-google`. Selectors copied
from the design would match nothing and the entire re-skin would silently no-op.

### M2 — Global reset lives in `design-tokens.css`, and the tokens are imported twice

**Constraint.** (a) The `* { box-sizing: border-box }` and `body { margin: 0 }` rules must end up
in `apps/web/src/styles/global.css`, not `design-tokens.css`. (b) Exactly **one** token load must
remain: `main.tsx` imports `./styles/design-tokens.css` **and** `global.css` line 1 is
`@import "./design-tokens.css";`. Remove one of them.

**Why.** design-02 locates the reset in the wrong file. The duplicate import double-applies the
whole token sheet and inflates the CSS bundle with no benefit.

### M3 — AppShell needs an explicit bounded height or the calendar breaks

**Constraint.** The `AppShell` root in `apps/web/src/components/MainLayout.tsx` must be given an
explicit bounded height (`height: 100dvh` with a `100vh` fallback, or equivalent). Its scroll
container needs `min-height: 0` and `overflow: auto`. Do **not** rely on the AppShell default.

**Why.** `AppShell` defaults to `min-height: 100dvh`, which imposes **no** height ceiling.
`MainLayout.tsx` currently uses `height: 100vh` with an inner `overflow: auto` scroller, and that
bounded box is what makes `<FullCalendar height="100%">` resolve to a viewport-sized calendar. With
only `min-height`, the `height: 100%` chain has no definite parent height, so the calendar grows to
its content height and the page scrolls instead of the calendar.

**Design gap.** design-03 mentions only `padding={0}` for this component; the height requirement is
undocumented.

### M4 — Mantine breakpoint names do not match the design's numbers

**Constraint.** Pick one and apply it consistently in **both** the `createTheme` breakpoints and
the PostCSS media queries in `global.css`:

- use Mantine's own names (`xs` / `md` / `lg`), or
- override `breakpoints` in `createTheme` so the names carry the design's intended values.

**Why.** The design's table maps `sm` to `36em`, but Mantine's default `sm` is `48em` (`xs` is
`36em`). Using the design's number under Mantine's `sm` name silently shifts every breakpoint by
12em, so the mobile Drawer / navbar collapse fires at the wrong width and the desktop/mobile
contract that keeps exactly one `<aside>` mounted (`M7`) can break at in-between widths.

### M5 — `eventContent` replaces FullCalendar's internal event DOM; existing selectors stop matching

**Constraint.** The new `eventContent` renderer must:

1. Keep the event title **inside** the `.fc-event` element (E2E asserts `.fc-event` containing the
   task title).
2. Emit stable, project-owned classes (e.g. `.brk-event-title`, `.brk-event-time`) and update
   `CalendarStyles.css` to target those instead of `.fc-event-title` / `.fc-event-time`.
3. Work for **both** `timeGridDay` / `timeGridWeek` **and** `dayGridMonth`.
4. Render all event kinds — task, block, generated, preview, external — each keeping its distinct
   colour and its `brk-*` class.
5. Stop the per-event delete button's `click` from also triggering `eventClick` (call
   `stopPropagation`, or move the control outside the clickable region).
6. Preserve the existing `classNames` (`brk-task`, `brk-generated`, `brk-external`, `brk-block`,
   `brk-preview`) or update every dependent selector in the same change.

**Why.** The current implementation injects DOM via `eventDidMount` (around lines 278–332) and
`CalendarStyles.css` styles FullCalendar's own `.fc-event-title` / `.fc-event-time` internals.
`eventContent` replaces those internals, so every title/time rule in the stylesheet silently dies.

### M6 — FullCalendar injects CSS at runtime; `!important` escalation must stop

**Constraint.** Drive calendar theming through **CSS custom properties** on the wrapper element
(the approach the design already specifies), not by adding more `!important` declarations. Do not
fight the cascade by raising specificity.

**Why.** FullCalendar `6.1.20` injects its own stylesheet into `<head>` at runtime, i.e. after the
app stylesheet has loaded. `apps/web/src/styles/CalendarStyles.css` already carries **17**
`!important` blocks — including three Google-red declarations at lines 41, 45 and 46 (design-04
claims two). Custom properties inherit and therefore win reliably regardless of injection order;
direct rules do not.

### M7 — Exactly one `<aside>` and one `TaskPanel` may be mounted at any viewport

**Constraint.** The document must contain **exactly one** `<aside>` element and **exactly one**
task panel at every viewport width, desktop and mobile. The responsive Drawer must not mount a
second copy of the sidebar while the Navbar copy is still in the DOM. Prefer a single sidebar
instance moved between the Navbar and the Drawer, or an `AppShell.Navbar` whose `collapsed.mobile`
state and the Drawer's open state are mutually exclusive.

**Preferred implementation.** `<aside>` wrapper (guaranteed to compile and to satisfy the locator)
around the sidebar content. `AppShell.Navbar component="aside"` is *probably* valid — all Mantine
components are built on `factory` and accept a polymorphic `component` — but this was **not
verified**; do not depend on it without typechecking first.

**Why.** `TASK-02.spec.ts` asserts a single `aside` and a single `Tasks (N)` panel. Mounting the
sidebar in both the Navbar and a Drawer produces duplicate panels and strict-mode violations.

### M8 — `ConflictDialog` must be unmounted when closed

**Constraint.** The migrated dialog must **not** remain in the DOM when closed. If a Mantine modal
is used, keep `keepMounted={false}` (the default) and ensure the component returns `null` / is not
rendered when `isOpen` is false — matching current behaviour, where `ConflictDialog.tsx` returns
`null`.

**Why.** `ConflictDialog.tsx` (86 lines) contains "preview" copy in multiple places, including a
discard action. `TASK-02.spec.ts` asserts `text=Preview` resolves to **exactly one** element and
that it is visible. A `keepMounted` modal leaves the text in the DOM and breaks the assertion;
`PreviewToolbar.tsx` owns the single legitimate visible "Preview" label.

### M9 — `DashboardPage.tsx` (567 lines) must be split, and has one owner across phases 4/5/6

**Constraint.** `apps/web/src/pages/DashboardPage.tsx` currently holds **567 lines** and already
breaches the project's 400-line rule. It must be decomposed during this delivery into focused
child modules (candidates: status-region collection → `StatusBar`, calendar view state and view
switching, preview orchestration handlers, slot-click handler, modal state owner).

**Single-owner rule.** Because phases 4, 5 **and** 6 all require changes to this file, it must
have **exactly one owning lane for the entire delivery**:

- **Recommended:** the Phase 4 owner performs the split as part of Phase 4, extracts stable prop
  interfaces, and phases 5 and 6 route their changes through those interfaces rather than editing
  `DashboardPage.tsx` directly.
- Alternative: designate one lane as the exclusive `DashboardPage.tsx` owner for phases 4–7 and
  gate every other lane's dashboard changes behind it.

Two lanes must **never** edit this file concurrently. Full procedure:
[`dispatch-plan.md`](./dispatch-plan.md#dashboardpage.tsx-single-owner-rule).

### M10 — design-06 omits three feature files from its Phase 6 file list

**Constraint.** Phase 6 must include these three files, which the design's migration list does not
mention:

- `apps/web/src/features/tasks/TaskCard.tsx` (69 lines)
- `apps/web/src/features/blocks/BlockCard.tsx` (65 lines)
- `apps/web/src/features/completion/CompletionAction.tsx` (42 lines)

They carry the same inline-style debt as the rest of Phase 6 and must be migrated, or explicitly
deferred with a recorded reason.

### M11 — `SettingsModal` renders ~400 timezone options; Mantine `Select` is not virtualized

**Constraint.** When migrating `components/SettingsModal.tsx` (263 lines), either keep a native
`<select>` for the timezone field, or add a search/filter affordance before switching to Mantine
`Select`. Do not blindly swap all three of its selects to non-virtualized Mantine `Select`s.

**Why.** `timezoneOptions` is built from `Intl.supportedValuesOf("timeZone")` (400+ entries) at
mount. Mantine `Select` renders every option into the dropdown DOM; this is a measurable
open-dropdown cost on a field users open often.

**Not E2E-constrained.** No spec asserts `SettingsModal` internals, so Mantine inputs are permitted
here (contrast with `B2`).

### M12 — E2E specs are outside the TypeScript program

**Constraint.** Never treat `build apps/web` as evidence that the E2E specs still typecheck or that
their selectors still resolve. `apps/web/tsconfig.json` **excludes `e2e`**. Only
`run-package-command test apps/web` validates the spec contract.

**Consequence.** Selector drift caused by `B1`, `B2`, `M5` or `M7` is invisible to the build and
surfaces only as a Playwright failure — or worse, not at all, if a locator silently resolves to a
different element.

### M13 — PostCSS pipeline ordering and stylesheet import order

**Constraint.** (a) The PostCSS pipeline lives in **`apps/web`** (Vite); `packages/ui` has no CSS
pipeline and must not gain one. (b) Import `@mantine/core/styles.css` in `main.tsx` **before**
`design-tokens.css`, `global.css` and `CalendarStyles.css`, so app-level rules win. (c) Keep the
numeric breakpoint values in `global.css` media queries identical to the Mantine theme breakpoints
(see `M4`).

**Why.** Importing Mantine styles after app styles silently inverts the override precedence, and
`postcss-preset-mantine` must run before other rules for Mantine variable substitution to apply.

### M14 — E2E runs against a reused dev server

**Constraint.** Before trusting any `test apps/web` result, ensure no stale dev server is bound to
the dev port. `playwright.config.ts` sets `reuseExistingServer: true`, so Playwright will silently
reuse a server started in an earlier phase and exercise a **stale bundle**.

**Why.** A stale server produces both false passes (old bundle still satisfies the assertions) and
false failures (already-fixed regressions still present). With `fullyParallel: false` and
`retries: 1`, a single such run can invalidate a whole phase sign-off.

### M15 — Five status regions, not four; and Header vs. CalendarToolbar ownership must be fixed

**Constraint — status regions.** `DashboardPage.tsx` contains **five** conditional UI regions
(success, error, calendar loading/error, allocation failure, preview/generation state). All five
must be absorbed by the new `StatusBar`. The design text alternates between "four inline banners"
and "five banners" — the code is authoritative: **five**.

**Constraint — ownership.** The date navigation and view switcher must have exactly one owner:

| Control | Owner | Rationale |
| --- | --- | --- |
| Brand, date-range title, `Today` | `AppShell.Header` | App-level navigation |
| `‹` / `›` date step, `Day` / `Week` / `Month` | `CalendarToolbar` | Calendar-specific |

**The calendar toolbar replaces the Header's navigation block entirely.** The Header must **not**
also render `‹`/`›` or the view switcher. `CalendarToolbar` renders the view switcher as real
buttons (`B1`). Note that replacing the visible `‹`/`›` glyphs with icons is iconography, not copy,
but the accessible names must be preserved.

**User decision:** this split is confirmed as a planning constraint.

### M16 — FullCalendar already implements sticky day headers

**Constraint.** Do not add custom sticky-position CSS for the calendar's day-header row until the
built-in behaviour has been observed. If custom sticky styling is still required, scope it so it
cannot fight FullCalendar's own mechanism (`.fc-sticky`, applied by JS via `getStickyHeaderDates`
in the timegrid plugin).

**Why.** FullCalendar `timegrid@6.1.20` computes and applies sticky header positioning in JS.
Competing CSS produces jitter, doubled offsets, or headers that detach during scroll.

### M17 — `CalendarStyles.css` (181 lines) will breach the 400-line rule once re-skinned

**Constraint.** Plan the calendar CSS as **multiple focused files** from the start:
`CalendarStyles.css` (layout/grid) plus partials for tokens, events, and the dark tier, all
imported from `main.tsx`. Do not grow the single file and split it later.

**Why.** 17 `!important` blocks plus a three-tier token set plus event variants plus dark-tier
overrides in one file will exceed 400 lines.

### M18 — Two design-06 file paths are wrong

**Constraint.** Use the real paths:

- `apps/web/src/features/completion/TokenRetryModal.tsx` (115 lines) — **not** `components/`.
- `apps/web/src/features/completion/RefreshButton.tsx` (40 lines) — **not** `components/`.

**Why.** Copying the design's paths produces file-not-found errors and, worse, can lead to new
files being created at the wrong location with duplicate components.

Files touched by **more than one phase** or **more than one Phase 6 lane**. These are the files
the orchestrator must serialise.

| --- | --- | --- | --- | --- |
| **OVERLAP-1** | `apps/web/src/pages/DashboardPage.tsx` | 4, 5, 6 | Multi-phase write | **Single owner for the whole delivery** (`M9`). Never concurrent |
| **OVERLAP-2** | `apps/web/src/main.tsx` | 1, 2, 5, 7 | Multi-phase write | Own the provider additions in Phase 2 and the CSS import list in Phase 5; Phase 7 only removes dead rules. Serialise |
| **OVERLAP-3** | `apps/web/package.json` | 1, 3 | Multi-phase write | Phase 1 owns the Mantine/PostCSS deps; Phase 3 may only add the `packages/ui` peer. Serialise |
| **OVERLAP-4** | `pnpm-lock.yaml` | 1, 3 | Regenerated artifact | Any dependency change re-runs `pnpm install`. Never hand-edit; re-run after each manifest change |
| **OVERLAP-5** | `apps/web/src/styles/design-tokens.css` | 2, 7 | Multi-phase write | Phase 2 restructures it and removes the reset; Phase 7 only prunes dead rules. Serialise |
| **OVERLAP-6** | `apps/web/src/styles/global.css` | 2, 7 | Multi-phase write | Phase 2 receives the reset + breakpoint media queries; Phase 7 removes dead responsive classes. Serialise |
| **OVERLAP-7** | `apps/web/src/styles/CalendarStyles.css` | 5, 7 | Multi-phase write | Phase 5 rewrites it (and splits per `M17`); Phase 7 prunes. Serialise |
| **OVERLAP-8** | `apps/web/src/App.tsx` | 2, 6-C | Cross-phase | Phase 2 may add providers; Phase 6-C owns the Dev-mode/Login migration. If Phase 2 touched `App.tsx`, 6-C must rebase, not revert |
| **OVERLAP-9** | `packages/ui/src/index.ts` | 3, 6-B, 6-C | Multi-lane read, single-phase write | Only Phase 3 writes it. Lanes 6-B and 6-C only **consume** it — read-only |
| **OVERLAP-10** | `packages/ui/dist/**` | 3, 6 | Generated artifact | Never edit. Must be rebuilt before every `apps/web` build (`R-05`) |

**Files with NO overlap** (safe for concurrent Phase 6 lanes): the 23 files in the three lanes
defined in [`dispatch-plan.md`](./dispatch-plan.md#phase-6--definitive-lane-split). Each appears in
exactly one lane.

8 of the 10 flags are cross-**phase**, which is why phases 1–5 must be dispatched sequentially. Only
`OVERLAP-1` requires an ownership rule *within* the parallel phase.

## Breaking Changes

### To the E2E contract — none permitted; five constraints protect it

The suite must pass **unmodified**. The constraints that protect it:

- `B1` — view switcher stays `<button>` (`button:has-text("Day"/"Week")`).
- `B2` — native `<select>` / `<input>` preserved in `TaskModal` and `CreateActionModal`
  (`selectOption("#task-duration")`, `label:has-text("Duration (minutes)") select`,
  `fill("#task-name")`, submit-button locators).
- `M5` — event title stays inside `.fc-event`; `.fc-timegrid-slots`, `.fc-timegrid-body`,
  `.fc-timegrid-slot` (containing `14:00`) preserved.
- `M7` — exactly one `<aside>`, exactly one `Tasks (N)` panel.
- `M8` — exactly one visible `Preview`.

### To the public component API — none

`packages/ui`'s exported names (`Button`, `ButtonVariant`, `ButtonSize`, `Modal`, `FAB`,
`BottomSheet`) and their props must not change. Mantine's `opened` / `variant` / `size` naming is
mapped **inside** the wrappers.

### To application behaviour — none intended

Calendar view switching, slot-click creation, task CRUD, preview generation, settings persistence
and dev-mode auth all keep their current behaviour. Dark mode is additive.

## Decision Summary

### Selected Approach

Single delivery, 7 phases; phases 1–5 strictly sequential; phase 6 as 3 file-disjoint lanes; phase 7
sequential. 10 file-overlap flags identified with explicit handling. 18 material corrections
(`M1`–`M18`) recorded as mandatory constraints.

### Reasoning

The design touches ~30 frontend files but no backend, no database and no public API. The only
genuine scheduling hazards are the 10 overlapping files, all enumerable and serialisable — and 8 of
the 10 are cross-*phase*, already handled by making phases 1–5 sequential. Only `DashboardPage.tsx`
requires an explicit intra-phase ownership rule.

### Expected Outcome

Phases 1–5 produce a green build at every step; phase 6 runs three concurrent lanes with zero
shared writes; phase 7 removes dead CSS and records the bundle delta against the
524.63 kB / 156.62 kB baseline.

### Open Questions

None. Deferred by user decision and recorded as constraints: `B3` (`businessHours` deferral),
`M3` (bounded AppShell height), `M15` (Header/CalendarToolbar ownership split).
